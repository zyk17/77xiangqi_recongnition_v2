# 棋盘定位长期方案

## 1. 背景

当前仓库里的棋盘定位主线是：

```text
整图 -> board bbox -> 均匀切 9x10 -> piece_classifier
```

现状问题已经明确：

- `board_detector` 在合成训练/验证集上指标很好
- 真实场景整链表现明显不稳定
- `piece_classifier` 单独评估在真实裁剪棋盘上表现很好

因此当前主问题不是棋子分类，而是：

```text
如何从真实截图中稳定恢复主棋盘坐标系
```

## 1.1 已失败尝试复盘

截至目前，已经有两条主线被真实 `eval_cases` 证伪：

### 第一版：外框 `bbox -> 均匀切 9x10`

方案：

```text
image -> board bbox -> 在 bbox 内均匀切 9x10 -> piece_classifier
```

为什么失败：

- `bbox` 不是最终真正需要的几何对象
- 外框语义不稳定，模型容易学成“找到中间那块大棋盘面板”
- `bbox` 即使看起来差不多对，均匀切格对边界误差极敏感
- 合成集上的 `bbox IoU` 好，并不等于真实 90 格裁切稳定

结论：

- 第一版能学会“棋盘大概在哪”
- 但不能稳定恢复可用于裁 90 格的网格坐标系

### 第二版：直接回归 `x[9], y[10] + types[90]`

方案：

```text
image -> geom[19] + types[90]
```

为什么失败：

- 任务被定义成全局参数回归，给了模型走捷径的空间
- 模型更容易拟合“棋盘模板参数”，而不是学习局部交点、棋子、线结构证据
- 合成指标可以很好，但真实图上仍然容易整体 ROI 偏移、整体坐标系错位

真实现象：

- `train_type_acc / val_type_acc` 持续上升
- 真实 `eval_cases` 上整链仍明显失败
- overlay 显示错误更偏向“整盘坐标系整体猜偏”，而不是局部点位读图成功

结论：

- 第二版证明了“直接回归全局参数”不是最终可行主线
- 后续版本必须显式引入空间证据监督，而不能只靠全局回归

## 2. 长期目标

新方案不再以 `bbox` 为核心目标，而是直接服务于后续 90 格裁剪。

长期目标定义为：

```text
整图 -> 主棋盘格点坐标系 -> 向外扩半格 -> 裁 90 格 -> piece_classifier
```

其中：

- `dx` = `cell_w` = 相邻两列交点中心距离
- `dy` = `cell_h` = 相邻两行交点中心距离
- 单个格子裁剪框基于交点中心向外扩 `0.5 * dx` / `0.5 * dy`

即：

```text
x1 = cx - 0.5 * dx
x2 = cx + 0.5 * dx
y1 = cy - 0.5 * dy
y2 = cy + 0.5 * dy
```

## 3. 已确定原则

### 3.1 任务定义

本轮不再继续投入 `bbox regression` 主线。

新的棋盘定位任务定义为：

- 恢复主棋盘 `9x10` 格点坐标系
- 区分每个格点是：
  - `piece`
  - `cross`

说明：

- `piece` 与 `cross` 在语义上互斥
- 当前阶段不引入 `ignore` 标签，棋盘检测训练数据不做棋盘内部遮挡增强

### 3.2 结构约束

新方案不能退回“传统算法先找很多点/线，再靠复杂几何后处理拼坐标系”的路线。

因此模型与数据设计必须满足：

- 主棋盘只有一套坐标系
- 输出必须天然受 `9x10` 结构约束
- 不能允许开放式输出大量自由候选点，再靠复杂筛选补锅

### 3.3 数据优先

这次方案成败首先取决于数据，而不是骨架。

优先级顺序为：

1. 棋盘素材标注契约
2. 合成数据标签定义
3. 正负样本边界
4. 干扰分布设计
5. 模型输出形式与 loss

## 4. 推荐主线

### 4.1 第 2.5 / 第 3 版方向

第三版不再直接回归整套 `x[9], y[10]`。

新的主线要求是：

- 模型必须先输出局部空间证据
- 再由轻量结构恢复逻辑得到唯一主棋盘坐标系

推荐主线：

- 输出空间证据图，而不是只输出全局参数
- 证据图优先考虑：
  - `piece` 证据图
  - `cross` 证据图
  - 可选 `line` / `h-line` / `v-line` 证据图
- 再由这些证据恢复主棋盘 `9x10` 坐标系

不建议继续使用：

- 主棋盘 `bbox` 作为最终中间表示
- 直接回归整套 `x[9], y[10] + types[90]` 作为唯一主线
- 自由候选点 + 重传统几何后处理

### 4.2 为什么转向空间证据图

目标不是让模型“猜一套棋盘模板”，而是让模型被迫利用：

- 交点信息
- 棋子占位信息
- 线结构信息

也就是说，后续版本必须能回答：

- 为什么这里是一个交点
- 为什么这里是一条线
- 为什么这里有棋子/没有棋子

只有这样，恢复出来的网格坐标系才有机会在真实图上稳定。

### 4.3 备线

备线允许保留：

- 行列投影
- 线结构辅助分支
- 4 点 / 内框角点实验

但都不应回到“候选线条很多，再人工几何拼装”的老路。

## 5. 数据契约

### 5.1 棋盘素材标注

对每套 `data/raw/boards/{name}/board.xxx`，新增一份素材元数据。

首选标注内容：

```json
{
  "grid_roi": [x1, y1, x2, y2]
}
```

含义：

- `grid_roi` 是主棋盘有效网格区域
- 不包含外框、牌匾、底座、主题装饰
- 用于等距推导 `9` 列和 `10` 行的交点中心

如果个别棋盘内部并不满足规则等距，再升级成更精细元数据，例如：

```json
{
  "grid_x": [x0, x1, ..., x8],
  "grid_y": [y0, y1, ..., y9]
}
```

当前第一阶段默认先标 `grid_roi`。

### 5.2 合成样本标签

每个合成样本至少要能导出：

- 主棋盘交点中心坐标
- 每个格点的类型标签

建议标签结构：

```json
{
  "grid_roi": [x1, y1, x2, y2],
  "grid_points": [
    [{"x": 0.0, "y": 0.0, "label": "cross"}, ...],
    ...
  ]
}
```

也可以拆成更适合训练读取的结构，只要语义不变：

- `x[9]`
- `y[10]`
- `labels[10][9]`

### 5.3 标签定义

每个格点只允许以下两种状态之一：

- `piece`
  - 当前格点被棋子占用
- `cross`
  - 当前格点为空，且视觉证据足够清晰

约束：

- `piece` 与 `cross` 互斥
- 不要求模型学习“棋盘内部被挡住后的猜测能力”
- 因此棋盘检测训练数据不加入棋盘内部遮挡增强

## 6. 正负样本边界

### 6.1 正样本

只有主棋盘 `9x10` 坐标系上的合法格点可以成为正样本：

- 主棋盘 `piece`
- 主棋盘 `cross`

### 6.2 负样本

以下内容全部视为背景负样本，不做正标注：

- 棋盘外圆形按钮、头像、徽章
- 棋盘外线条交叉、表格角点、装饰十字
- 棋盘外文字和笔画交会
- 副棋盘、小棋盘、缩略棋盘
- 棋盘外任意近似棋子/交点的结构

说明：

- 这些元素可以存在于图中
- 但不应成为第二套合法坐标系
- 本轮决定：不专门做小棋盘增强

## 7. 数据增强策略

### 7.1 保留并重点覆盖

应保留并重点覆盖：

- 棋盘位置随机
- 棋盘尺度随机
- 宽屏/窄屏布局
- 上下左右留白
- 棋盘外 UI 面板
- 圆形图标/头像/按钮
- 棋盘外文字
- 棋盘外线条与表格感结构
- 中残局、残局、随机非法布局
- 不同棋盘主题
- 不同棋子皮肤

### 7.2 弱化或删除

本轮明确不做：

- 专门的小棋盘/副棋盘增强
- 棋盘内部遮挡增强

原因：

- 它属于高风险干扰
- 容易把任务再次拉回“多棋盘候选 + 几何筛选”
- 它会迫使模型学习被挡住时的猜测行为
- 当前阶段更重要的是先把主棋盘坐标系恢复做稳

### 7.3 干扰设计原则

棋盘外干扰可以很像：

- 棋子
- 交点
- 线结构

但必须满足两点：

1. 它们全部是负样本背景
2. 干扰强度要贴近真实 UI，而不是为了“刁难模型”而堆砌随机伪结构

## 8. 模型输出与训练建议

### 8.1 输出建议

第三版推荐输出分为两层：

第一层：空间证据

- `piece` 证据图
- `cross` 证据图
- 可选 `line` / `h-line` / `v-line` 证据图

第二层：结构恢复

- 由证据图恢复主棋盘 `9x10` 坐标系
- 再生成 90 格裁切框

这样做的目的：

- 强迫模型真正学习局部视觉证据
- 避免再次退化成全局模板参数拟合
- 保留结构约束，但不让结构约束替代视觉理解

### 8.2 loss 方向

loss 设计重点：

- 证据图损失
  - 监督 `piece/cross/line` 的空间响应
- 结构恢复损失
  - 监督恢复后的网格坐标系
- 结构一致性损失
  - 保证 `x`、`y` 单调
  - 保证相邻间距平滑

### 8.3 数据层额外要求

第三版除了改输出形式，还需要补一类数据能力：

- 非棋盘区域的背景复杂度必须更贴近真实手游/APP 场景

当前合成图的棋盘外区域仍偏简单，后续要增强：

- 背景插画/场景图
- 顶部信息条、底部操作条
- 半透明叠层
- 高对比头像/角色立绘
- 小图标密集区域

目标是让模型在训练时就看到“复杂但非棋盘”的背景，而不是只见到较干净的留白和简单块状 UI。

## 9. 参考 pipeline 目标形态

参考串联目标应调整为：

```text
image
-> board localization model
-> 9x10 grid points
-> 每点向外扩半格
-> 90 cells
-> piece_classifier
```

其中 Python 参考实现需要服务两件事：

- 验证数据与模型方案是否成立
- 给 Rust 提供稳定直接的参考逻辑

## 10. 阶段计划

### 阶段 1：数据定义与素材标注

- 完成棋盘素材 `grid_roi` 标注
- 定义新标签格式
- 改造数据生成与增强

### 阶段 2：失败路线复盘完成

- 第一版 `bbox` 路线失败原因固化
- 第二版 `geom[19] + types[90]` 路线失败原因固化
- 明确下一版不能继续停留在全局参数回归

### 阶段 3：第三版最小闭环

- 训练带空间证据图输出的新定位模型
- 跑通证据图输出 + 网格恢复
- 接回现有 `piece_classifier`

### 阶段 4：真实评估与收敛

- 用真实 `eval_cases` 评估整链
- 补失败模式
- 固化导出和参考推理

### 阶段 5：Rust 对接 demo

- 明确 ONNX 输入输出契约
- 明确裁格逻辑
- 交付一份完整 demo

## 11. 成功标准

成功标准不再以 `bbox IoU` 为主，而应以整链效果为主：

- 主棋盘格点恢复稳定
- 90 格裁剪稳定
- 真实 `eval_cases` 上整链准确率明显高于当前 `bbox` 方案
- Python 参考实现足够直接，可迁移到 Rust
